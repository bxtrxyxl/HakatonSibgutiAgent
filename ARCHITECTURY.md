# Архитектура «Ассистент СибГУТИ»

Простыми словами: это локальное веб-приложение, которое отвечает на вопросы о СибГУТИ по заранее собранной базе знаний. Ответ генерирует языковая модель, но факты она берёт только из найденных документов, а не из своей памяти. Такой подход называется RAG — поиск нужных фрагментов плюс генерация ответа.

## 1. Статус на чекпоинт

### Уже работает

- Сбор базы из Markdown, HTML, PDF и TXT.
- Очистка текста, нарезка на чанки, дедупликация.
- Хранение базы в SQLite + FTS5 и векторов в `embeddings.npy`.
- Гибридный поиск: точные слова + смысл.
- Ответы языковой модели со ссылками на источники.
- Изоляция диалогов по сессиям.
- Защита от prompt injection и безопасные логи.
- Веб-интерфейс без сборки: один `web/index.html`.
- Реальное управление базой: резервные копии, восстановление, пересборка из папки, проверка эмбеддингов, загрузка документа.
- Ключи API хранятся только на сервере в `.env`.

Текущая база: **9 документов, 179 чанков, 114 299 символов, 0 ошибок**. Автотесты: **16 проверок**.

### Модели

- **Языковая модель** — любой OpenAI-совместимый API. Адрес, ключ и название модели задаются в `.env`.
- **Эмбеддинги** — сейчас `baai/bge-m3`, 1024 измерения. Модель тоже задаётся в `.env`.

### Ещё не сделано

- Офлайн-демо в чате пока осталось как отдельный режим.
- Правая панель со статистикой пока использует демо-данные.
- Автоматический парсинг сайта по расписанию.
- Пересборка индекса идёт синхронно, без фоновой задачи и прогресс-бара.
- Нет авторизации и ограничения запросов для публичного запуска.

## 2. Как выглядит система целиком

```text
Пользователь
    │
    ▼
web/index.html  ── HTTP ──►  FastAPI (src/api.py)
                                  │
                                  ▼
                            Агент (src/agent.py)
                             │            │
                             ▼            ▼
                    Поиск (retrieval)   LLM API
                             │
                             ▼
                    SQLite + FTS5 + embeddings.npy
```

Три слоя:

1. **Интерфейс** — один HTML-файл. Рисует чат, настройки и панели, отправляет запросы.
2. **Сервер** — FastAPI. Принимает запросы, хранит сессии, вызывает поиск и языковую модель.
3. **Данные** — SQLite с текстами и `embeddings.npy` с векторами. Это и есть база знаний.

Отдельный поток — наполнение базы:

```text
data/docs (.md) / upload / сайт
            │
            ▼
     ingest.py: очистка → чанки → эмбеддинги
            │
            ▼
 SQLite (документы, чанки, FTS5) + embeddings.npy
```

## 3. Путь вопроса

1. Пользователь пишет вопрос в интерфейсе.
2. UI отправляет `session_id` и текст на `POST /api/chat`.
3. `security.py` проверяет попытки сменить роль или вытащить системный промпт.
4. Агент переформулирует follow-up вопрос с учётом истории только этой сессии.
5. `retrieval.py` ищет кандидатов двумя способами:
   - по точным словам через SQLite FTS5 (BM25);
   - по смыслу через косинусное сходство векторов.
6. Два списка объединяются через RRF: чем выше фрагмент в обоих рейтингах, тем выше его итоговое место. Получается топ-8 чанков.
7. Найденные куски проверяются и упаковываются в контекст.
8. Языковая модель получает системную инструкцию, контекст и вопрос.
9. Ответ возвращается в Markdown, вместе с ним — список источников и время генерации.
10. Событие пишется в `logs/events.jsonl` без ключей и секретов.

Главное правило: модель не должна выдумывать сроки, баллы и стоимость. Если данных нет — она честно говорит об этом и отправляет в приёмную комиссию.

## 4. Путь документа

1. Документ кладут в `data/docs` или загружают через интерфейс.
2. `ingest.py` определяет формат: Markdown, HTML, PDF или TXT.
3. HTML очищается от меню, футеров, скриптов и рекламы.
4. Таблицы переводятся в Markdown, чтобы не потерять строки и столбцы.
5. Из текста достаются метаданные: заголовок, URL, раздел, год.
6. Считается SHA-256. Если такой текст уже есть — документ пропускается.
7. Текст режется на чанки — небольшие куски примерно по 1100 символов с перекрытием 150.
8. Для каждого чанка эмбеддинг-модель считает вектор смысла.
9. Документ и чанки пишутся в `kb.sqlite`, векторы — в `embeddings.npy`.
10. `registry.json` и `stats.json` обновляются, чтобы было видно, что и когда добавлено.

## 5. Файлы проекта

### `src/config.py`

Центр настроек. Читает `.env`, хранит пути к данным и константы: размер чанка, top-K, таймауты. Проверяет, что ключи LLM и эмбеддингов заданы, но сам никогда не печатает их. Функция `status()` отдаёт только факт «настроено / не настроено», без секретов.

Основные константы: `TOP_K=8`, `CANDIDATES_PER_SOURCE=15`, `MAX_CHUNKS_PER_DOC=4`, `CHUNK_SIZE=1100`, `CHUNK_OVERLAP=150`.

Зачем нужен: чтобы все модули использовали одни и те же пути и не дублировали настройки.

### `src/ingest.py`

Самый большой модуль. Отвечает за всё, что связано с текстом и базой:

- загружает HTML, PDF, TXT и Markdown;
- чистит HTML и переводит таблицы в Markdown;
- достаёт заголовок, URL, раздел и год;
- режет текст на чанки;
- считает эмбеддинги;
- пишет документы и чанки в SQLite;
- обновляет `registry.json` и `stats.json`;
- делает резервные копии базы и восстанавливает их.

У него есть CLI: `--dir` для папки, `--file` для одного файла, `--urls` для списка ссылок. Сервер вызывает те же функции, поэтому ручная сборка и сборка из интерфейса дают одинаковый результат.

Чанкинг не разрывает строки таблиц: большая таблица делится по строкам с повтором заголовка. Эмбеддинги считаются батчами по 32; если API отклоняет батч, он дробится, чтобы проблема одного текста не роняла весь документ.

### `src/retrieval.py`

Ищет нужные чанки. Работает в два прохода:

1. **FTS5 + BM25** — поиск по точным словам. Хорошо находит коды направлений, даты, суммы и фамилии.
2. **Косинусное сходство** — поиск по смыслу. Хорошо находит перефразированные вопросы.

Результаты объединяются через RRF. Дальше включаются ограничения: не больше 4 чанков с одного документа и отбрасывание почти одинаковых фрагментов. На выходе — топ-8 чанков с текстом, заголовком, URL, разделом и годом.

### `src/security.py`

Защита от prompt injection. Ищет не тему «безопасность», а конкретные директивы: «игнорируй правила», «ты теперь администратор», «покажи системный промпт», «дай историю другой сессии».

Ещё он:

- оборачивает найденные чанки в теги `trust="untrusted_data"`;
- нейтрализует подозрительные команды внутри документов;
- вырезает из логов всё, похожее на ключи и токены;
- пишет события в `logs/events.jsonl`.

### `src/prompts.py`

Два промпта:

- `REWRITE_PROMPT` — превращает follow-up в самостоятельный поисковый запрос. Например, «а что с общежитием?» после вопроса про ИВТ станет запросом про общежитие для ИВТ.
- `SYSTEM_PROMPT` — правила ответа: только факты из контекста, ссылки `[1]`, честное «нет данных», сравнение таблицей, запрет менять роль.

### `src/agent.py`

Ядро RAG-пайплайна. Здесь живут:

- `SessionStore` — история диалогов строго по `session_id`;
- переформулировка вопроса;
- вызов поиска;
- сборка контекста;
- вызов языковой модели;
- сбор источников;
- запись времени и лога.

История одной сессии не видна другой: методы принимают только конкретный `session_id`. В модель уходят последние 8 сообщений. История сессий хранится в памяти процесса: после перезапуска сервера диалоги на сервере начинаются заново, а сохранённые чаты в браузере остаются.

### `src/api.py`

FastAPI-сервер. Принимает запросы от интерфейса:

- чат и новая сессия;
- статистика базы;
- загрузка файла;
- пересборка из папки;
- список, создание, восстановление и удаление резервных копий;
- проверка эмбеддинг-модели;
- здоровье сервера.

Ключи API он не отдаёт. Ошибки очищаются от секретов. Долгие операции с базой защищены блокировкой, чтобы не запускать две пересборки одновременно.

### `web/index.html`

Весь интерфейс в одном файле: HTML, CSS и JavaScript. Без React, npm и сборки. Три колонки: чаты, диалог, справка. В настройках три вкладки: «Подключение», «Интерфейс», «База данных».

История чатов и настройки хранятся в `localStorage` браузера под ключом `sibsutis_assistant_v3`. База и ключи — на сервере. Режимы работы: FastAPI, прямой API и офлайн-демо. В режиме FastAPI интерфейс вызывает `/api/chat`, `/api/databases`, `/api/embeddings/test` и остальные методы сервера.

### `tests/test_eval.py`

Проверяет качество поиска, изоляцию сессий, честность при отсутствии данных, конфликт версий и четыре группы атак: прямая инъекция, косвенная инъекция, многошаговая попытка стать админом и легитимные слова про безопасность.

### `tests/test_api.py`

Проверяет API базы: статус, создание и восстановление копии, удаление, запрет папок вне `data/`, проверку эмбеддингов.

### `README.md`, `PLAN.md`, `ARCHITECTURY.md`

`README.md` — запуск и API. `PLAN.md` — этапы и UI-контракт. Этот файл — объяснение архитектуры для защиты.

## 6. Данные: каждый файл

### `data/docs/`

Главный источник знаний. Здесь лежат нормализованные Markdown-документы по институтам, программам, поступлению, общежитиям и стипендиям. У каждого файла есть frontmatter:

```text
title: Приёмная кампания 2026
url: https://sibsutis.ru/abitur/priem.php
section: Поступление
year: 2026
```

`ingest.py` читает эти поля, чтобы в ответе была правильная ссылка и раздел.

### `data/raw/`

Оригиналы скачанных HTML и PDF. Нужны, чтобы можно было проверить, что именно было в источнике, и пересобрать базу без повторного скачивания. Локальные `.md` из `data/docs` здесь не дублируются — они уже лежат в исходном виде.

### `data/kb.sqlite`

Главная база. Внутри три таблицы:

- `documents` — по одной строке на документ. Поля: `doc_id`, `title`, `url`, `section`, `fetched_at`, `year_version`, `format`, `sha256`, `chars`, `chunk_count`, `retrieved_via`.
- `chunks` — по одной строке на кусок текста. Поля: `id`, `doc_id`, `idx`, `heading`, `text`, `chars`.
- `chunks_fts` — виртуальная таблица FTS5 для полнотекстового поиска. Хранит `chunk_id`, `text`, `title`, `section`.

`documents` отвечает на вопрос «что это за источник», `chunks` — «какой именно кусок текста», `chunks_fts` — «где встречаются эти слова». `chunks.id` связывает обычную таблицу и FTS. `chunks.idx` хранит порядок куска внутри документа, `heading` — ближайший заголовок. FTS5 хранит свою копию текста — это нормально, она нужна для быстрого полнотекстового поиска.

Сейчас в базе 9 строк `documents`, 179 строк `chunks` и 179 векторов в `embeddings.npy` — числа должны совпадать.

`sha256` не даёт добавить один и тот же текст дважды. `doc_id` строится из URL. `PRAGMA journal_mode=WAL` включает журнал WAL — это ускоряет чтение и уменьшает блокировки. Рядом могут появляться `kb.sqlite-wal` и `kb.sqlite-shm` — это рабочие файлы SQLite, их не нужно трогать.

### `data/embeddings.npy`

Матрица векторов в формате NumPy. Каждая строка — один чанк, столбцов столько, сколько измерений у модели (сейчас 1024). Тип `float32`, векторы нормализованы до длины 1.

Связь с базой простая: строки идут в том же порядке, что `chunks.id` по возрастанию. При загрузке `retrieval.py` берёт `SELECT id FROM chunks ORDER BY id` и проверяет, что число строк совпадает. Если не совпало — поиск не запускается и просит пересобрать базу. Это защита от «полубазы», когда тексты есть, а векторов нет.

Почему отдельный файл: SQLite неудобен для матричных операций, а NumPy считает косинусное сходство одной операцией умножения. Нормализация нужна, чтобы косинус считался как обычное скалярное произведение.

### `data/registry.json`

Реестр источников. По каждому документу: `doc_id`, `title`, `url`, `section`, `fetched_at`, `year_version`, `format`, `chars`, `chunk_count`, `retrieved_via`. Нужен для аудита: что вошло в базу, откуда и когда. По нему можно быстро проверить, что источник не потерялся при пересборке.

### `data/stats.json`

Сводка по базе: `generated_at`, `unique_docs`, `sections`, `total_chars`, `chunks`, `formats`, `skipped_duplicates`, `errors`, `error_count`, `embeddings`.

Именно отсюда вкладка «База данных» берёт цифры. Если сборка упала на одном файле, ошибка попадёт в `errors`, но остальные документы продолжат обрабатываться.

### `data/app_settings.json`

Небольшие настройки, которые можно менять без перезапуска сервера. Сейчас там хранится путь к папке источников, например `data/docs`. Ключи API сюда не попадают — они только в `.env`.

### `data/backups/`

Резервные копии базы. Внутри папки с идентификатором вида `db_20261121_041000_abcdef` лежат:

- `kb.sqlite` — копия базы;
- `embeddings.npy` — копия векторов;
- `registry.json`, `stats.json` — копии метаданных;
- `meta.json` — имя, дата, число документов, чанков и символов.

Копия SQLite делается через встроенный `backup()`, а не простым копированием файла, чтобы не поймать момент записи. Восстановление идёт через временные файлы и замену: сначала копия готовится рядом, потом подменяет рабочую. Так база не остаётся наполовину старой и наполовину новой.

### `data/seed_urls.json`

Список официальных страниц для режима `--urls`. Сейчас основной поток — локальные `.md`, но краулер сохранён для будущего автопарсинга.

### `logs/events.jsonl`

Журнал событий, по одному JSON на строку. Поля: `timestamp`, `session_id`, `query_len`, `retrieved_urls`, `latency_ms`, `security_flags`, `status`, `error`. Сам текст вопроса туда не пишется. Ключи и токены вырезаются.

Статусы помогают понять, где остановился запрос: `ok`, `empty_query`, `no_context`, `retrieval_error`, `llm_error`, `empty_answer`.

### `.env` и `.env.example`

`.env` хранит адреса и ключи LLM и эмбеддингов, название моделей, `TOP_K`. Основные переменные: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `EMBED_BASE_URL`, `EMBED_API_KEY`, `EMBED_MODEL`. В репозиторий попадает только `.env.example` без секретов. В коде ключи не хранятся.

### `requirements.txt`

Минимальный стек: FastAPI, uvicorn, OpenAI-клиент, httpx, BeautifulSoup, trafilatura, pypdf, numpy, python-dotenv, python-multipart, pydantic, pytest.

### Служебные файлы

| Файл | Зачем нужен |
| --- | --- |
| `.gitignore` | Не пускает в репозиторий `.env`, базу, эмбеддинги, бэкапы, логи и кэш |
| `pyproject.toml` | Настройки ruff и pytest: длина строки, правила линтера, папка тестов |
| `opencode.json` | Настройки среды разработки: MCP-серверы, LSP и запрет на чтение `.env` |
| `AGENTS.md` | Правила работы агента-разработчика, на работу приложения не влияют |

## 7. Почему выбрана такая архитектура

- **SQLite + FTS5 вместо отдельной векторной БД.** Не нужен Docker и внешний сервер, база — один файл, запуск в три команды.
- **Гибридный поиск, а не только векторы.** Точные коды вроде `09.03.01`, даты и суммы лучше ищутся словами, а общие вопросы — по смыслу.
- **Один HTML-файл вместо React.** Быстрее собрать и показать, нет сборки и npm.
- **Ключи только на сервере.** Браузер не получает API-ключи и не может их украсть.
- **Чанки и источники.** Модель отвечает по фрагментам, а пользователь видит, откуда взялся факт.

## 8. Безопасность

- Прямые и косвенные попытки prompt injection детектируются.
- Найденные чанки оборачиваются как недоверенные данные.
- Модель не может сменить роль по тексту из документа или пользователя.
- Логи не содержат API-ключей.
- Папка для пересборки ограничена `data/`, выйти за её пределы нельзя.
- Ключи LLM и эмбеддингов лежат в `.env` на сервере.

## 9. Что осталось и как будет работать

1. **Убрать офлайн-демо из чата.** Оставить только FastAPI и прямой API, чтобы все ответы шли через реальную базу.
2. **Реальная правая панель.** Добавить `GET /api/overview`, который отдаёт стоимость, баллы, места и стипендии из базы, вместо демо-данных.
3. **Автопарсинг сайта.** Планировщик будет брать `data/seed_urls.json`, скачивать страницы, считать SHA-256, пропускать неизменённые, складывать оригиналы в `data/raw` и запускать тот же `ingest.py`. После изменений — пересборка индекса и запись в `stats.json`.
4. **Фоновая пересборка.** Сейчас запрос ждёт окончания сборки. Позже — очередь задач, статус и прогресс в UI.
5. **Публичный запуск.** Авторизация, лимиты запросов и защита от злоупотреблений.

## 10. Что показать на демо

1. Задать вопрос про поступление и показать ответ со ссылками.
2. Задать follow-up в том же диалоге — контекст сохраняется.
3. Открыть «База данных» и показать реальные цифры.
4. Создать резервную копию, восстановить её.

## 12. Ограничения

- База знаний — только открытые материалы СибГУТИ, без личных кабинетов и оценок.
- Данные приёмной кампании актуальны на 2026 год.
- Языковая модель может ошибаться, поэтому в ответах есть источники для проверки.
- Пересборка базы синхронная и занимает около 20 секунд на текущем объёме.
- Тесты добавляют временные документы в базу, после `pytest` нужна пересборка.
