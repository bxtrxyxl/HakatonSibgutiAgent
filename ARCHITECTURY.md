# Архитектура «Ассистент СибГУТИ»

Простыми словами: это локальное веб-приложение, которое отвечает на вопросы о СибГУТИ по заранее собранной базе знаний. Ответ генерирует языковая модель, но факты она берёт только из найденных документов, а не из своей памяти. Такой подход называется RAG — поиск нужных фрагментов плюс генерация ответа.

## Статус на чекпоинт

### Уже работает

- Сбор базы из Markdown, HTML, PDF и TXT.
- Очистка текста, нарезка на чанки, дедупликация.
- Хранение базы в SQLite + FTS5 и векторов в `embeddings.npy`.
- Гибридный поиск: точные слова + смысл.
- Ответы языковой модели со ссылками на источники.
- Изоляция диалогов по сессиям.
- Защита от prompt injection и безопасные логи.
- Веб-интерфейс без сборки: один `web/index.html`.
- Реальное управление базой: резервные копии, восстановление, пересборка из папки, проверка эмбеддингов, загрузка документа.
- Ключи API хранятся только на сервере в `.env`.

Текущая база: **9 документов, 179 чанков, 114 299 символов, 0 ошибок**. Автотесты: **16 проверок**.

### Ещё не сделано

- Офлайн-демо в чате пока осталось как отдельный режим.
- Правая панель со статистикой пока использует демо-данные.
- Автоматический парсинг сайта по расписанию.
- Пересборка индекса идёт синхронно, без фоновой задачи и прогресс-бара.
- Нет авторизации и ограничения запросов для публичного запуска.

## Модели

- **Языковая модель** — любой OpenAI-совместимый API. Адрес, ключ и название модели задаются в `.env`.
- **Эмбеддинги** — сейчас `baai/bge-m3`, 1024 измерения. Модель тоже задаётся в `.env`.

## Общая схема

```text
Пользователь
    │
    ▼
web/index.html  ── HTTP ──►  FastAPI (src/api.py)
                                  │
                                  ▼
                            Агент (src/agent.py)
                             │            │
                             ▼            ▼
                    Поиск (retrieval)   LLM API
                             │
                             ▼
                    SQLite + FTS5 + embeddings.npy
```

Отдельный поток — наполнение базы:

```text
data/docs (.md) / upload / сайт
            │
            ▼
     ingest.py: очистка → чанки → эмбеддинги
            │
            ▼
 SQLite (документы, чанки, FTS5) + embeddings.npy
```

## Как работает ответ на вопрос

1. Пользователь пишет вопрос в интерфейсе.
2. UI отправляет `session_id` и текст на `POST /api/chat`.
3. `security.py` проверяет попытки сменить роль или вытащить системный промпт.
4. Агент переформулирует follow-up вопрос с учётом истории только этой сессии.
5. `retrieval.py` ищет кандидатов двумя способами:
   - по точным словам через SQLite FTS5 (BM25);
   - по смыслу через косинусное сходство векторов.
6. Два списка объединяются через RRF: чем выше фрагмент в обоих рейтингах, тем выше его итоговое место. Получается топ-8 чанков.
7. Найденные куски проверяются и упаковываются в контекст.
8. Языковая модель получает системную инструкцию, контекст и вопрос.
9. Ответ возвращается в Markdown, вместе с ним — список источников и время генерации.
10. Событие пишется в `logs/events.jsonl` без ключей и секретов.

Главное правило: модель не должна выдумывать сроки, баллы и стоимость. Если данных нет — она честно говорит об этом и отправляет в приёмную комиссию.

## Как наполняется база

- Источники лежат в `data/docs` в Markdown.
- `ingest.py` умеет также HTML, PDF и TXT.
- Текст очищается от меню, футеров, скриптов и мусора.
- Таблицы переводятся в Markdown, чтобы они нормально попадали в ответы.
- Текст режется на чанки — небольшие куски примерно по 1100 символов с перекрытием 150.
- Одинаковые документы отбрасываются по SHA-256.
- Для каждого чанка считается вектор эмбеддинг-моделью.
- Документы и чанки пишутся в SQLite, векторы — в `embeddings.npy`.
- `registry.json` хранит источники, `stats.json` — статистику.

## Почему выбрана такая архитектура

- **SQLite + FTS5 вместо отдельной векторной БД.** Не нужен Docker и внешний сервер, база — один файл, запуск в три команды.
- **Гибридный поиск, а не только векторы.** Точные коды вроде `09.03.01`, даты и суммы лучше ищутся словами, а общие вопросы — по смыслу.
- **Один HTML-файл вместо React.** Быстрее собрать и показать, нет сборки и npm.
- **Ключи только на сервере.** Браузер не получает API-ключи и не может их украсть.
- **Чанки и источники.** Модель отвечает по фрагментам, а пользователь видит, откуда взялся факт.

## Модули

| Файл | Что делает |
| --- | --- |
| `src/config.py` | Пути, `.env`, константы |
| `src/ingest.py` | Сбор, очистка, чанкинг, SQLite, эмбеддинги, снапшоты |
| `src/retrieval.py` | Гибридный поиск: BM25 + косинус → RRF |
| `src/security.py` | Детектор инъекций, санитайзер, логи |
| `src/prompts.py` | Системный промпт и переформулировка вопроса |
| `src/agent.py` | Сессии, RAG-пайплайн, источники, тайминги |
| `src/api.py` | FastAPI: чат, база, загрузка, эмбеддинги |
| `web/index.html` | Интерфейс: чат, панели, настройки, база |

## Управление базой

Вкладка «База данных» в настройках работает по-настоящему, без имитации:

- **Активная база** — показывает документы, чанки, символы и папку.
- **Резервные копии** — сохраняют `kb.sqlite`, `embeddings.npy`, реестр и статистику в `data/backups/<id>/`.
- **Восстановление** — заменяет файлы базы через временные копии, чтобы не оставить её полусломанной.
- **Эмбеддинг-модель** — сервер проверяет API и возвращает модель, размерность и задержку. Ключ в браузер не уходит.
- **Папка `.md`** — можно указать папку внутри `data/` и полностью пересобрать индекс.
- **Импорт документа** — файл загружается на сервер и добавляется в базу.

## Безопасность

- Прямые и косвенные попытки prompt injection детектируются.
- Найденные чанки оборачиваются как недоверенные данные.
- Модель не может сменить роль по тексту из документа или пользователя.
- Логи не содержат API-ключей.
- Папка для пересборки ограничена `data/`, выйти за её пределы нельзя.
- Ключи LLM и эмбеддингов лежат в `.env` на сервере.

## Что показать на демо

1. Задать вопрос про поступление и показать ответ со ссылками.
2. Задать follow-up в том же диалоге — контекст сохраняется.
3. Открыть «База данных» и показать реальные цифры.
4. Создать резервную копию, восстановить её.
5. Нажать «Проверить модель» и показать реальный ответ embedding API.
6. Пересобрать базу из папки `data/docs`.

## Ограничения

- База знаний — только открытые материалы СибГУТИ, без личных кабинетов и оценок.
- Данные приёмной кампании актуальны на 2026 год.
- Языковая модель может ошибаться, поэтому в ответах есть источники для проверки.
- Пересборка базы синхронная и занимает около 20 секунд на текущем объёме.
- Тесты добавляют временные документы в базу, после `pytest` нужна пересборка.
